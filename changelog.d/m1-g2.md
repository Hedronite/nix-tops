### Added

- `nixtops check` reads `nix-tops.toml`, validates it against `schema/nix-tops.schema.json` (embedded at build time, one source), and runs the section 12 checks that need no outputs: a failure exits 2 and names its key. It refuses `facet` (a profile key), an unknown key, a wrong type and an unknown facet; refuses `enforce = "advisory"` (protocol 0.2.0 has no exemption key); fails an expired `[[warnings.allow]]` entry, a missing baseline under `ratchet`, and a `nix-tops` input that follows nixpkgs in `flake.lock`; reports each facet as profile found, specified-unproven or no profile; and exits 3 when the host Nix is below the daemon floor.
- `nixtops init --facet <f>` writes `nix-tops.toml`, `.github/workflows/nix-tops.yml` (from `config/workflow.template.yml`) and the `AGENTS.md` section between the template's markers. It prints the `flake.nix` lines and never edits `flake.nix`, refuses to overwrite without `--force`, and a second run is byte-identical. Goldens for each facet live in `crates/nixtops/tests/goldens/`.
- Facet profiles are embedded from `profiles/`, one `include_str!` per file, with a test that fails on a profile file that is not embedded. `config::schema::validator` is public so the report check can validate through it.

### Added (phase 2)

- `nixtops check` reads the flake's outputs with the kit's pinned judge (`inventory::structure_of`) and checks that each listed facet is one the outputs show and that `[toolchain].systems` equals the systems they export; either mismatch exits 2 and names the key (`facets[n]`, `toolchain.systems`). `fleet-root` and `image` are refused with exit 2 and the message says M1 does not derive them. An output whose members cannot be listed, a flake that cannot be read, and a build with no pinned judge exit 3.
- Under `ratchet`, `check` requires the baseline to be tracked and clean against `HEAD` with one `git` read: a missing `git` exits 3; a directory that is not a repository, an untracked baseline, or a baseline that differs from `HEAD` exits 2. Other modes do not check it.
- `check::evaluate_with_outputs(config, today, nix, &Structure) -> Verdict` is the entry point `check` and `gate` call; `evaluate` stays for the checks that need no outputs.
- `nixtops init` takes its facets and systems from the outputs, narrowed by `--facet`, which may only name a facet the outputs show. Cheap refusals (an unknown facet, an existing file without `--force`) come before the outputs are read. A flake that exports an unsupported system is refused. A build with no pinned judge keeps the `--facet` and three-system fallback and prints a note that the systems are not verified and that `nixtops check` will verify them against the outputs.

### Not derived in M1

- `home-config` is derived from `homeConfigurations` only, not from Home Manager as a NixOS or nix-darwin module (section 5.1); `check` says so when `home-config` is listed. `fleet-root` and `image` are not derived.
